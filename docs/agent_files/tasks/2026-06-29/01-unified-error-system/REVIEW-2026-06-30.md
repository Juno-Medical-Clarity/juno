## Prioritized Issues

### Low severity

1. **`AthenaAPIError` status-code mapping diverges from Task 01.6 literal spec**
   (`backend/models/external_api/athena_errors.py:13-21`, raise sites in
   `backend/services/external_api/athena_client.py:52,88,103,105`).
   Task 01.6 required the 401/429/404/else → ErrorCode mapping *inside* `__init__`, with
   acceptance `AthenaAPIError(429, …).error_code == ATHENA_RATE_LIMIT_ERROR` etc. The
   current (SP03/04-refactored) class instead takes an explicit `code=ErrorCode.ATHENA_API_ERROR`
   default and the mapping was pushed to call sites. So `AthenaAPIError(429, "x")` with no
   `code` now yields `ATHENA_API_ERROR`, not `ATHENA_RATE_LIMIT_ERROR` — the literal Task 01.6
   assertions would fail. Functionally equivalent in practice: callers pass the right code and
   `test_athena_client.py` asserts the correct `error_code` for auth/rate-limit/non-200 paths.
   The SP01 core goal (JunoError subclass → uniform classification → KeyError fix) is fully met.
   Treat as a downstream-evolution note, not an SP01 regression.

2. **404 → `ATHENA_PATIENT_NOT_FOUND` mapping is no longer applied**
   (`backend/services/external_api/athena_client.py:103` — `raise AthenaAPIError(resp.status_code, resp.text)`
   passes no `code`). A 404 from a clinical GET is classified `ATHENA_API_ERROR` (502) rather
   than `ATHENA_PATIENT_NOT_FOUND` (404). PRD §4d listed 404→ATHENA_PATIENT_NOT_FOUND. The
   catalog entry exists and is correct; only the call-site wiring omits it. Minor latent
   misclassification, no crash.

3. **PRD §7 listed three exception-identity tests not co-located in `tests/errors/test_exceptions.py`**
   (`test_athena_api_error_is_juno_error`, `test_missing_job_config_error_is_juno_error`,
   `test_gcs_fetch_required_is_juno_error`). TASKS.md Task 01.5's explicit test list omitted
   them, so this matches the task spec, but the PRD §7 listing is not fully reproduced in the
   errors suite. Coverage effectively exists elsewhere: `tests/services/external_api/test_athena_client.py`
   asserts `error_code` on the JunoError subclass, and `tests/utils/test_cloud_tasks.py` /
   `test_preset_data.py` pass. No functional gap, only test-placement divergence.
