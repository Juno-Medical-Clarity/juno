## Implementation issues

### Minor (non-blocking)

1. **[routes/care_plan.py:66] `_UPLOAD_PREFIX = "simplify-uploads"`** — The GCS *fetch* prefix for looking up existing uploaded files by `doc_id` is still `"simplify-uploads"`. The *save* path (line 77) correctly uses `care_plan/{user_id}/inputs/...`, but the `_fetch_from_gcs` function reads from `{_UPLOAD_PREFIX}/{doc_id}/` which points at the old `simplify-uploads` bucket folder. PRD §4.4 says rename the GCS blob prefix `simplify/...` → `care_plan/...`; this one stale constant was missed. Not production-critical (no data exists), but inconsistent with the PRD intent.

2. **[routes/batch.py:200] Hardcoded `"__result__"` sentinel instead of importing `RESULT_SENTINEL`** — `care_plan.py` defines `RESULT_SENTINEL = "__result__"` at module level. `batch.py` duplicates the string literal inline (`chunk[0] == "__result__"`) rather than importing the constant. If the sentinel is ever renamed, `batch.py` will silently break (the tuple sentinel would be ignored, causing every batch run to report "Pipeline did not return a result"). Low risk today but a maintenance coupling hazard.

3. **[utils/juno_metrics.py:12-16, 63, 96, 102, 124, 129, 153] Docstring examples still reference old metric names** — The module-level docstring and method docstring examples still show `"simplify_request"`, `"simplify_pipeline"`, and `"simplify_pipeline"` as example metric names. PRD §4.4 says update these docstrings to the new `care_plan_*` names. SP4 owns the module internals; if SP4 has not landed, SP2 is supposed to update these. The call sites in routes have been correctly renamed (no `simplify_request` / `simplify_pipeline` appears in route code), but the docstrings were not updated.

4. **[utils/juno_logger.py:13] Docstring example references `/simplify/v1-2`** — The module-level docstring example still shows `path="/simplify/v1-2"`. PRD §4.4 says update to `path="/care_plan"`. Same SP4 boundary issue as above; cosmetic but was explicitly called out in the PRD.

5. **[routes/batch.py:202-208] `CarePlanInternal` constructed without `before_score`/`after_score`** — When the batch route intercepts the sentinel tuple, it destructures as `_, care_plan, grading, *_` (discarding trailing elements) and constructs `CarePlanInternal(metrics, input_model, grading, care_plan)` — omitting `before_score` and `after_score`. The model defaults both to `None`, so no crash occurs, but grading scores are silently dropped from batch outputs even when `grading_enabled=True`. This means `before_score`/`after_score` are absent from all batch `output_data` payloads. This is likely intentional (batch was not supposed to return scores in the envelope previously), but it is not explicitly addressed in the PRD and diverges from the main care_plan route behavior.

### Structural (test infrastructure — does not affect production code)

6. **[tests/routes/__init__.py and tests/models/__init__.py] Shadow package collision prevents `pytest` from running most tests** — Both `tests/routes/__init__.py` and `tests/models/__init__.py` are empty `__init__.py` files that Python treats as packages named `routes` and `models`. When pytest adds the `tests/` directory to `sys.path` during collection, `import routes` resolves to `tests/routes` (an empty package without `all_blueprints`) instead of `backend/routes`. This causes:
   - `tests/conftest.py` line 13 (`from routes import all_blueprints`) to fail with `ImportError`
   - All pytest-collected tests that use `from routes import ...` or `from models import ...` to fail during collection
   - `tests/test_simplify_v1_2_pipeline_schema.py` and `tests/test_models_care_plan.py` (pytest-style tests with no `sys.path` manipulation) to fail

   All the old-style `test_*.py` files in `tests/` work around this by explicitly manipulating `sys.path` before their imports, but `conftest.py` does not. The new `tests/routes/*.py` and `tests/models/*.py` files also have `sys.path` manipulation in each file, so they run correctly when invoked directly or through `python file.py`, but **cannot be discovered via `python -m pytest tests/` as currently configured**.

   The fix is to add `pythonpath = ["."]` to `[tool.pytest.ini_options]` in `pyproject.toml`, which makes pytest add `backend/` to `sys.path` before collection, so `import routes` finds `backend/routes/__init__.py` first.
