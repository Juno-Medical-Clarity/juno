# PRD: Core Output Envelope Refactor

Sub-project 1 of 5. **Foundational — every other sub-project depends on this shape.**

## 1. Problem

Today each pipeline route (`simplify.py` for v1, `simplify_v1_1.py`, `simplify_v1_2.py`) builds one flat
dict by hand (`result = {**structured, "terms": ..., "raw": ..., "before_score": ..., "after_score": ...}`)
and emits it as the SSE `result` payload, then persists the same dict verbatim to Firestore
(`simplify_outputs.output_data`). There is no reusable model behind this shape — every field is added
ad hoc, nothing is independently testable or serializable, and there's no place to add new
cross-cutting sections (grading-as-its-own-thing, raw input capture, observability metadata)
without bolting more keys onto the same flat dict.

The session/logging ID (`g.session_id`, already generated by `app.py`'s `before_request` hook and
echoed via the `X-Session-Id` header) is never included in the JSON body, so the frontend can't show
it or let a user hand it to support/engineering when reporting an issue.

## 2. Goals

- Define four independent, JSON-serializable model classes: `Metrics`, `Input`, `Grading`,
  `SimplifiedCarePlan`.
- Combine them into one envelope (`SimplifyOutput`) that becomes the new shape of the SSE `result`
  payload and the Firestore `output_data` field.
- Surface the session/logging ID to the frontend inside `Metrics`.
- Keep this sub-project scoped to *plumbing* — `Grading` is a stub here (real schema lands in
  sub-project 3); `Input` only needs to cover today's input modes (file/text/doc_id), batch mode is
  added in sub-project 4.

## 3. Non-Goals

- Not changing what the pipeline computes — same LLM calls, same scoring, same steps.
- Not changing the route URLs (`/simplify/v1`, `/v1-1`, `/v1-2` still exist after this sub-project;
  they're collapsed in sub-project 2).
- Not building the Grading toggle/config UI (sub-project 3).
- Not migrating old Firestore documents — they keep their legacy flat shape forever (decision below).

## 4. Architecture Decisions

**Where models live.** New package `backend/models/`:
```
backend/models/
  __init__.py
  base.py        # JsonModel, VersionedJsonModel
  metrics.py     # Metrics
  input.py       # Input
  grading.py     # Grading (stub — empty entries list)
  care_plan.py   # SimplifiedCarePlan
  envelope.py    # SimplifyOutput
```

**Base class.** `JsonModel` is a plain dataclass mixin with `to_dict()` / `from_dict(data)`. No
external dependency (no Pydantic) — the codebase doesn't use Pydantic today and pulling it in just
for this is more than the task needs; dataclasses + manual `to_dict`/`from_dict` is enough and keeps
the diff small.

`VersionedJsonModel` adds a `version: str` field and a small per-class registry
(`@VersionedJsonModel.register("1.2")` decorator) so `SimplifiedCarePlan.from_dict(data)` can resolve
the right subclass by reading `data["version"]`. **Only `SimplifiedCarePlan` uses this.** Per the
versioning discussion: a model only needs version-dispatch when old and new instances require
*different parsing logic*. `Metrics`, `Input`, and `Grading` are additive data bags — new optional
fields are fine, old records simply lack them — so they get plain `JsonModel`, no version field, no
registry. This directly encodes the answer to "should everything be versioned?": no, only the report.

**`Metrics` (not versioned, always latest shape):**
```python
@dataclass
class Metrics(JsonModel):
    session_id: str            # the ID from g.session_id / X-Session-Id header — now in the body too
    pipeline_version: str       # "v1" | "v1-1" | "v1-2" (renamed "api_version" for clarity)
    input_type: str             # "file" | "text" | "doc_id" (batch added in sub-project 4)
    created_at: str             # ISO8601, set when the envelope is assembled
    total_duration_ms: float | None = None
    step_durations_ms: dict[str, float] = field(default_factory=dict)
    saved_id: str | None = None   # filled in after Firestore save, same as today's result["saved_id"]
```
Everything in `Metrics` is safe to expose — none of it is sensitive, so there's no separate
"public subset" filtering step. The user only asked for the ID specifically, but step durations are
already logged via `JunoLogger`/`JunoMetrics` today and are harmless to also surface in the response
body, and doing so means the frontend's future "view logs" feature in the user's plan needs only this
one field instead of a second redaction layer that wasn't asked for and adds no value here.

**`Input` (not versioned):**
```python
@dataclass
class Input(JsonModel):
    mode: str                   # "file" | "text" | "doc_id"
    text: str | None = None             # verbatim, when mode == "text"
    doc_id: str | None = None           # verbatim, when mode == "doc_id"
    files: list[InputFile] = field(default_factory=list)   # when mode == "file"

@dataclass
class InputFile(JsonModel):
    filename: str
    content_type: str
    size_bytes: int
```
**Decision flagged for confirmation:** `Input` stores file *metadata* (filename/type/size), not raw
bytes. The combined PDF is already uploaded to GCS (`input_pdf_gcs`) and referenced from the saved
output — duplicating raw bytes into the Firestore document as well would bloat documents (Firestore
has a 1 MiB document size limit) for no benefit, since the GCS reference already lets you retrieve the
original. "Store it as it is" is interpreted here as *don't transform or derive it* (i.e. capture the
exact filenames/text the user submitted, not a summarized version) rather than *duplicate the bytes
into a second location*. Flagged in TASKS.md as a checkpoint to confirm with you before Task 3.

**`Grading` (not versioned, stub in this sub-project):**
```python
@dataclass
class Grading(JsonModel):
    entries: list[dict] = field(default_factory=list)   # real schema arrives in sub-project 3
```
Wired into the envelope now so sub-project 3 only has to populate `entries`, not touch the envelope
shape again.

**`SimplifiedCarePlan` (versioned — "1.0" / "1.1" / "1.2"):**
Wraps the dict each pipeline already produces (`structured` + `terms` + `raw` + `before_score` +
`after_score`). The model's job is packaging, not re-validating the LLM-produced schema (that
validation already happens via the JSON schema files under `backend/simplify/*/`. Rewriting that as
strict per-field dataclasses would be a large, separate effort with no behavior change — out of scope
here):
```python
@dataclass
class SimplifiedCarePlan(VersionedJsonModel):
    version: str                # "1.0" | "1.1" | "1.2"
    data: dict                  # the existing structured/terms/raw/before_score/after_score dict, as-is

    @classmethod
    def from_pipeline_result(cls, version: str, data: dict) -> "SimplifiedCarePlan":
        return cls(version=version, data=data)

    def to_dict(self) -> dict:
        return {"version": self.version, **self.data}   # flattened — see "wire shape" below
```
Note `to_dict()` flattens `data` back up next to `version` rather than nesting it under a `data` key.
This keeps the V1.2 appointment-note shape exactly as the frontend already expects it
(`diagnosis`, `medications`, `terms`, etc. as direct siblings), so `AppointmentNoteV12View.tsx` needs
only one change: read these fields from `output.simplified_care_plan` instead of `output` directly,
not a deeper restructure of every field access.

**`SimplifyOutput` envelope:**
```python
@dataclass
class SimplifyOutput(JsonModel):
    metrics: Metrics
    input: Input
    grading: Grading
    simplified_care_plan: SimplifiedCarePlan

    def to_dict(self) -> dict:
        return {
            "metrics": self.metrics.to_dict(),
            "input": self.input.to_dict(),
            "grading": self.grading.to_dict(),
            "simplified_care_plan": self.simplified_care_plan.to_dict(),
        }
```
This `to_dict()` output is exactly what goes into the SSE `{"step": "result", "data": ...}` payload and
into `save_simplify_output(output_data=...)`.

**Legacy shape coexistence (no migration script — confirmed decision).** Old Firestore documents
saved before this change have the flat shape (`{diagnosis: ..., medications: ..., before_score: ...}`
with no `metrics`/`input`/`grading`/`simplified_care_plan` keys). New documents have the nested
envelope shape. Both must render correctly:
- `GET /simplify/saved/<doc_id>` returns the stored dict unchanged either way — no backend branching
  needed, it already just returns whatever was stored.
- The frontend gets a `normalizeSimplifyOutput()` adapter (Task 11) that detects which shape it
  received (`"simplified_care_plan" in data` → new; otherwise → legacy) and returns a consistent
  in-memory `SimplifyOutput`-shaped object either way, so every other frontend component only ever
  deals with one shape.

**Where `Metrics`/`Input` get their data from request handling.** `pipeline_version` comes from the
existing `api_version` already passed to `JunoLogger(api_version=...)` in each route. `step_durations_ms`
is collected by accumulating each `juno_logger.log_step(..., duration_ms=...)` call's value into a
dict at the route level (the route already computes each `duration_ms` for logging — this just also
keeps it). `session_id` comes from `g.session_id` (already set by the `before_request` hook).

## 5. API Change Summary

No URL changes in this sub-project. `/simplify/v1`, `/v1-1`, `/v1-2`, and `/simplify` (default-version
dispatcher) all change their **response body shape** from flat to the nested envelope. The
`X-Session-Id` header keeps being sent too (no reason to remove a working mechanism; the body field is
additive for frontend convenience).

Before:
```json
{ "doc_type": "appointment_note", "diagnosis": {...}, "before_score": {...}, "saved_id": "..." }
```
After:
```json
{
  "metrics": { "session_id": "...", "pipeline_version": "v1-2", "input_type": "file", "created_at": "...", "total_duration_ms": 4213.5, "step_durations_ms": {"find_medical_terms": 812.1, "...": 0}, "saved_id": "..." },
  "input": { "mode": "file", "files": [{"filename": "visit.pdf", "content_type": "application/pdf", "size_bytes": 88210}] },
  "grading": { "entries": [] },
  "simplified_care_plan": { "version": "1.2", "doc_type": "appointment_note", "diagnosis": {...}, "before_score": {...}, "...": "..." }
}
```

## 6. Frontend Change Summary

- New types mirroring the backend models (`frontend/src/types/envelope.ts`).
- `normalizeSimplifyOutput()` util so every consumer (live SSE result, saved-output loader) speaks one
  shape regardless of legacy vs new storage.
- `AppointmentNoteV12View` (and V1/V1.1 equivalents) read from `simplified_care_plan` instead of the
  envelope root.
- Small, unobtrusive "Request ID: `<session_id>`" line added to the report view, sourced from
  `metrics.session_id` — this is the concrete fulfillment of "share the logging ID with the frontend."
